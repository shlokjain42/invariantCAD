`createEvaluator()` creates the orchestration layer that validates documents,
resolves expressions, solves sketches, calls a geometry kernel, and exposes
owned outputs.

## Create an evaluator

```ts
const evaluator = await createEvaluator();
```

The default preserves the original behavior: it uses the bundled Manifold
kernel and built-in reference sketch solver. Named profiles add a complete
creation-time runtime gate:

```ts
const preview = await createEvaluator({ profile: "mesh-preview" });
const exact = await createEvaluator({ profile: "mechanical-exact" });
```

Both profiles require kernel protocol version 1 and callable `box`,
`cylinder`, and `sphere` primitives.

- `mesh-preview` creates Manifold and requires a mesh representation plus
  `extrude`, `revolve`, `boolean`, and `transform`.
- `mechanical-exact` creates stock OCCT and requires an exact B-Rep
  representation; the `extrude`, `revolve`, `loft`, `sweep`,
  `circularArcSweep`, `compositeSweep`, `boolean`, `transform`, `fillet`,
  `chamfer`, `shell`, and `offset` features; native `step`, `brep`, and
  `brep-binary` import and export through `importShape` and `exportShape`; and
  topology snapshots through a callable `topology()` whose capabilities cover
  faces, edges, and vertices with semantic roles, sketch sources, geometry, and
  adjacency.

A supplied custom kernel is checked against the same profile before an
evaluator is returned. `manifold` options are allowed only without a profile or
with `mesh-preview`, and `occt` options only with `mechanical-exact`; any other
combination throws `TypeError`. When you supply `kernel`, no kernel is created,
so `manifold` and `occt` options are not used.

Use `inspectEvaluatorProfile(kernel, profile)` when an application needs to
show missing capabilities without attempting evaluator creation. The returned
report is immutable and contains stable capability paths.

Both kernel and solver boundaries can still be replaced:

```ts
const evaluator = await createEvaluator({
  kernel: await createOcctKernel(),
  sketchSolver: customSolver,
});
```

If you supply a kernel or solver, the evaluator takes ownership of it and
disposes it when `evaluator.dispose()` is called.

A custom sketch solver is held to its declared protocol during evaluation:

- Before solving a sketch, the evaluator requires every entity and constraint
  kind in it to appear in `sketchSolver.capabilities.entities` or
  `.constraints`. An unadvertised kind fails with `KERNEL_CAPABILITY_MISSING`
  at `/nodes/<sketch>/entities/<id>` or `/nodes/<sketch>/constraints/<id>`,
  and `solve` is not called.
- `SolvedSketch.status` is authoritative. Only `solved` and `underconstrained`
  with a finite `residual` produce geometry. `overconstrained` fails with
  `SKETCH_OVER_CONSTRAINED` at `/nodes/<sketch>/constraints`; `nonconvergent`,
  `invalid`, a non-finite residual, and any unrecognized status fail with
  `SKETCH_SOLVE_FAILED` at `/nodes/<sketch>`. These failures are scoped to the
  sketch node even when the solver returned no error diagnostic.
- When the solver does return an error-severity diagnostic, the first one is
  reported, scoped to the sketch node, instead. If that diagnostic has no
  `path`, the evaluator sets it to `/nodes/<sketch>`. The reference solver
  reports its own over-constraint at `/nodes/<sketch>/constraints` and a
  non-finite residual at `/nodes/<sketch>`.

If a supplied kernel fails profile preflight, no evaluator takes ownership and
the caller remains responsible for disposing that kernel. A profile-created
kernel is disposed automatically if creation fails.

## Evaluation options

```ts
const controller = new AbortController();

const result = await evaluator.evaluate(document, {
  configuration: "manufacturing",
  parameters: { width: 120, thickness: 5 },
  outputs: ["body", "assembly"],
  signal: controller.signal,
  allowEmpty: false,
  topologySignatureLimits: {
    maxCandidatePairs: 50_000,
  },
});
```

| Option | Meaning |
| --- | --- |
| `configuration` | Exact document-owned configuration ID; omission selects the base design |
| `parameters` | Overrides by parameter ID: finite numbers in document base units, or expressions of the parameter's dimension such as `mm(120)` |
| `outputs` | Evaluate only the named output closure instead of every output |
| `signal` | Cooperative cancellation signal |
| `allowEmpty` | Accept zero-volume feature results: `EMPTY_RESULT` becomes a warning instead of an error, and an empty solid can be returned as an output |
| `topologySignatureLimits` | Bound persistent-reference matching work |

Unknown output, parameter, or configuration IDs produce diagnostics. Duplicate
output names in the option array are normalized rather than evaluated twice. An
explicitly empty `outputs` array always fails with `OUTPUT_MISSING`, whatever
`allowEmpty` is set to.

## Result handling

Evaluation returns a discriminated `CadResult`:

```ts
const result = await evaluator.evaluate(document);

if (!result.ok) {
  for (const diagnostic of result.diagnostics) {
    console.error({
      code: diagnostic.code,
      severity: diagnostic.severity,
      path: diagnostic.path,
      message: diagnostic.message,
      hints: diagnostic.hints,
      details: diagnostic.details,
    });
  }
  return;
}

try {
  const body = result.value.output("body");
  // Use body while the EvaluatedDesign is live.
} finally {
  result.value.dispose();
}
```

Warnings may accompany a successful result. For example, a BOM can be valid
while warning that a part number or material label is missing.

## Output classes

`EvaluatedDesign.output(name)` returns one of:

- `EvaluatedSolid`
- `EvaluatedPart`
- `EvaluatedAssembly`

Solids provide `mesh`, `measure`, `topology`, and `export`. Parts add material,
physical mass, and single-item BOM behavior. Assemblies expose occurrences,
aggregate geometry, physical properties, and nested BOM rollups.

## Ownership and disposal

An evaluation may allocate many native intermediate shapes. The successful
`EvaluatedDesign` owns all shapes retained for its outputs. Dispose the design,
not individual outputs.

```ts
result.value.dispose();
result.value.dispose(); // safe no-op

// body.measure() now throws because its owner is disposed.
```

`dispose()` marks the design disposed before it releases anything, then
attempts every owned shape exactly once. If a kernel release throws, the
remaining shapes are still released, the first error is rethrown, and the
design stays disposed, so a retry is a no-op. A failed evaluation releases the
shapes it created in the same best-effort way and still returns its original
diagnostics.

Use `try/finally`; do not rely on garbage collection to release WASM memory.

The shapes belong to the evaluator's kernel. `evaluator.dispose()` disposes
that kernel, which releases or invalidates every shape it still holds, so a
live `EvaluatedDesign` then fails on `measure()`, `mesh()`, and exports.
Dispose every evaluated design before the evaluator that produced it.

## Cancellation

Pass an `AbortSignal` to stop work you no longer need. Evaluation runs on the
calling thread, so the evaluator observes the signal at stage boundaries instead
of interrupting work:

- It checks the signal before each feature node and again after that node's own
  kernel work, so an abort raised synchronously by a kernel, solver, or topology
  callback stops evaluation before the next feature reaches the kernel.
- When a `signal` is supplied, it yields to the host event loop before geometry
  work starts, between selected outputs, and after the last output. An abort
  from a timer, a UI handler, `AbortSignal.timeout(...)`, or a worker message
  can land only at these yields.
- It forwards the signal to protocols that check it during their own work, such
  as sketch solving and profile-region validation.

Host code cannot run while one output's feature graph is being evaluated, so a
host abort issued during that time is observed when that output finishes. A
single synchronous native WASM call is never interrupted. An aborted evaluation
returns `EVALUATION_ABORTED` and releases every shape it created, including
finished outputs.

Because other code can run at those yields, an evaluation that receives a
`signal` first captures its request. It admits the document through the same
bounded snapshot as `parseDocumentValue(document)`, using the default
[document preflight limits](/evaluation/diagnostics-and-limits#document-preflight-limits),
and copies the options while keeping the same `signal`. Changing the caller's
document, `outputs` array, or other options after `evaluate(...)` returns its
promise does not affect that evaluation. A document that exceeds a limit or
does not match its version's schema fails with `IR_INVALID` before any geometry
work. Evaluations without a `signal` never yield, so they read the document
directly as before.

For hard latency isolation, or to stop one large output mid-run, evaluate in a
worker or separate process that the host can terminate. See
[browser and workers](/evaluation/browser-and-workers).

## Reuse

An evaluator can process multiple documents and variants sequentially. Results
remain independently owned and must each be disposed. While an evaluation that
received a `signal` is waiting at one of its event-loop yields,
`evaluator.dispose()` throws; await the evaluation first, aborting it if you no
longer need the result. Kernel runtime module initialization may be shared
internally, but shape ownership is never shared
implicitly across evaluated designs.
