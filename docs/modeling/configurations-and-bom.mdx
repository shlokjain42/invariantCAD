Configurations are definition-scoped named overrides stored inside the design
document. They do not clone the feature graph.

## Complete executable workflow

This canonical module builds a two-instance assembly, selects a named
configuration that changes its width, suppresses one occurrence, substitutes
its material, and verifies the resulting BOM.

{/* docs-example:start assembly-configuration-bom */}

```ts
import {
  EvaluatedAssembly,
  createEvaluator,
  design,
  kgPerCubicMeter,
  mm,
  tf,
  vec3,
} from "invariantcad";

const cad = design("configured-bracket-pair");
const width = cad.parameter.length("width", mm(40), { min: mm(10) });
const bracketSolid = cad.box("bracket-solid", {
  size: vec3(width, mm(20), mm(5)),
});
const aluminum = cad.material("aluminum", {
  name: "Aluminum",
  massDensity: kgPerCubicMeter(2_700),
});
const steel = cad.material("steel", {
  name: "Steel",
  massDensity: kgPerCubicMeter(7_850),
});
const bracket = cad.part("bracket", bracketSolid, {
  partNumber: "BRACKET-001",
  materialRef: aluminum,
});
const pair = cad.assembly("pair", (assembly) => {
  assembly.instance("left", bracket);
  assembly.instance("right", bracket, {
    placement: [tf.translate(vec3(mm(60), mm(0), mm(0)))],
  });
});
const wideSteelSingle = cad.configuration(
  "wide-steel-single",
  (configuration) => {
    configuration.parameter(width, mm(50));
    configuration.instanceSuppressed(pair, "right");
    configuration.partMaterial(bracket, steel);
  },
);
cad.output("pair", pair);

async function evaluateConfiguredAssembly() {
  const evaluator = await createEvaluator();
  try {
    const result = await evaluator.evaluate(cad.build(), {
      configuration: wideSteelSingle,
      outputs: ["pair"],
    });
    if (!result.ok) {
      throw new Error(
        result.diagnostics.map((item) => item.message).join("\n"),
      );
    }

    try {
      const output = result.value.output("pair");
      if (!(output instanceof EvaluatedAssembly)) {
        throw new Error("Expected the 'pair' output to be an assembly");
      }
      const bom = output.billOfMaterials();
      if (!bom.ok) {
        throw new Error(
          bom.diagnostics.map((item) => item.message).join("\n"),
        );
      }
      return {
        configurationId: result.value.configurationId,
        activeInstances: output.instances.map((instance) => instance.id),
        totalQuantity: bom.value.totalQuantity,
        materialId: bom.value.items[0]?.materialId,
        totalMassKg: bom.value.totalMass,
      };
    } finally {
      result.value.dispose();
    }
  } finally {
    evaluator.dispose();
  }
}

export const assemblyConfigurationBomSummary =
  await evaluateConfiguredAssembly();
console.log(assemblyConfigurationBomSummary);
```

{/* docs-example:end assembly-configuration-bom */}

The release gate compiles and executes the source module from
`examples/docs/assembly-configuration-bom.ts`. A configuration must contain at
least one override; duplicate overrides inside one configuration are rejected
during authoring.

After serialization, applications select the same variant by its stable ID:

```ts
const result = await evaluator.evaluate(parsedDocument, {
  configuration: "wide-steel-single",
});
```

`EvaluatedDesign.configurationId` records the active configuration or is
`null` for the default document context.

## Override categories

| Override | Scope | Effect |
| --- | --- | --- |
| Parameter | Document parameter | Re-evaluates every dependent effective feature |
| Instance suppression | One assembly definition and instance ID | Removes/adds that occurrence everywhere the definition is instantiated |
| Part material | One part definition | Changes density/material identity for every occurrence of that part |

Configuration overrides are definition-scoped. If the same subassembly is
instanced twice, suppressing an instance inside that subassembly definition
affects both placements. Per-occurrence effectivity is roadmap work.

## Deterministic BOM

The BOM:

- excludes suppressed occurrences
- groups shared part definitions deterministically
- rolls nested quantities through the occurrence tree
- includes part number, description, material identity, density source,
  occurrence IDs, and mass information when available
- composes affine placement for physical-property aggregation

Missing density does not invent a zero mass. Physical-property methods return a
diagnostic result explaining which part or material prevented a complete
rollup.

## Repository-only Document v7 part authoring and evaluation

The source tree contains a staged authoring and evaluation path for Document v7
outputs that directly reference a part. `stagedBodySetDesignV7(...)` now exposes
source-only length, angle, mass-density, and scalar parameters;
`transform(...)`, `translate(...)`, `rotate(...)`, `scale(...)`, and
`mirror(...)` solid authoring; `material(...)`; `part(...)`; configuration
`.partMaterial(...)`; and direct part `output(...)`. This is executable
protocol evidence, not a public package workflow: the package-root builder,
document alias, evaluator aliases, CLI, and migration target remain v6.

A staged part's geometry must be one owned solid DAG rooted in a box, cylinder,
sphere, or imported-body leaf, or one owned body set composed from those solid
DAG roots. The only admitted internal solid node is an ordered transform.
Transforms can be chained and parameterized by length, angle, or scalar
expressions. Parts cannot wrap another part, and the facade does not admit a
Boolean-produced solid or transform a body set, part, or assembly. Materials
and parts are builder-owned typed handles; foreign or forged handles are
rejected. New option records must be exact plain own-data records, and
accessor-backed or unknown fields are rejected without invoking them. Part,
material, configuration, and membership metadata is detached before the
document is deeply frozen.

The staged result preserves part number, description, detached metadata,
legacy material label, effective material definition, density, and density
source. Its geometry is explicitly either one retained solid or one retained
body set; the evaluator never chooses a primary body. Named configuration
material overrides select the effective material identity. Authored or
configured density parameters resolve in the selected configuration and may be
further specialized by bounded caller overrides. An explicit part density
takes precedence over the effective material's density, while a legacy
material label and material name remain descriptive and never supply inferred
density.

`billOfMaterials()` returns one deterministic part row with quantity one.
Missing density leaves its mass incomplete and produces a warning rather than
inventing zero. `physicalMassProperties()` requires one finite positive
density and, for a body set, applies it uniformly to every authored membership
before combining independent-body mass, center of mass, and inertia. Shared
solid aliases and spatially overlapping bodies each count once per
membership—the operation performs neither deduplication nor a Boolean union.
The numeric properties inherit the selected geometry backend's measurement
quality.

The part facade can merge tessellations and export STL or OBJ, all explicitly
approximate/lossy. Exact export and topology remain per-solid or per-body
capabilities. Aggregate geometric measurement, cross-body topology, exact
aggregate STEP/BREP, assemblies, occurrence rollups, interference handling,
per-body materials, Boolean inputs, and general part graphs beyond
primitive/import/transform DAGs are outside this staged slice. A primitive or
transformed solid cannot be a direct staged output; it must be retained by a
part or body set.

Stock OCCT evaluates native and imported transform DAGs as exact B-Rep when the
imported leaf satisfies the strong exact single-solid document-import
contract. Manifold evaluates native primitive/transform DAGs as approximate
mesh geometry and cannot stand in for that import boundary. Evaluation never
falls back between the two backends. Body-set and part evaluation separately
bound distinct leaves, all solid-graph nodes, transform input edges, and
authored transform operations with `maxDistinctSolids`,
`maxSolidGraphNodes`, `maxSolidDependencyLinks`, and
`maxTransformOperations`.

## Repository-only Document v7 nested local assemblies

The staged facade can wrap those admitted parts and already-completed local
assemblies in an acyclic fixed-placement assembly graph through `assembly(...)`
and its `StagedLocalAssemblyBuilderV7` callback, publish a containing assembly
as an output, and evaluate it with the source-only
`evaluateLocalAssemblyOutputsV7(...)` operation. A staged configuration can
call `instanceSuppressed(assembly, instanceId, suppressed?)`. The configuration
active for each containing assembly overrides that definition's authored
suppression; passing `false` therefore reactivates an instance authored as
suppressed.

This is deliberately different from widening the public v6 semantics described
above. Each staged v7 instance also carries one child configuration selector:

| Selector | Effective child context |
| --- | --- |
| `inherit` | The configuration active for the containing assembly |
| `base` | The base document, regardless of the containing assembly's context |
| `named` | The referenced document-owned named configuration |

That selected context controls a referenced child assembly's own suppression
and placement expressions, or a referenced part's geometry and product intent.
Caller parameter overrides then specialize every selected context for that one
evaluation. Active part leaves are emitted in authored depth-first order with
full root-to-leaf occurrence paths. Placement operations execute in authored
order on each edge and compose parent first into a root-relative transform.

The evaluator reuses one evaluated part result for equal
`(part, effective configuration)` states within the call, but keeps every full
occurrence path and quantity. Direct part evaluation may also acquire a solid
DAG once per configuration batch when multiple admitted parts reference it. It
does not infer geometric equivalence between contexts and establishes no
cross-run cache.

The contextual BOM keeps unlike `(part, effective configuration)` states in
separate deterministic rows. Each row records its stable full occurrence
paths, effective material and density provenance, definition mass, placed total
mass, and quantity. Occurrences sharing one context aggregate quantity
normally. Missing density leaves the affected row and overall total incomplete,
with diagnostics instead of an invented zero. Physical mass applies each
context's density to every single- or multibody part membership, then uses the
root-relative affine placement before combining mass, center of mass, and
inertia. Aliases and overlaps still count per authored membership and
occurrence; this is not interference subtraction or a Boolean union.

Suppression is decided before a component is admitted, so a suppressed nested
edge prunes its entire subtree, including external or otherwise unsupported
descendants. Traversal is bounded by `maxAssemblyDepth`,
`maxOccurrencePathSegments`, scanned-instance, active-occurrence, placement,
and downstream part/resource ceilings. The assembly-wide
`maxSolidGraphNodes`, `maxSolidDependencyLinks`, and
`maxTransformOperations` counters charge each `(solid node, effective
configuration)` once across the active tree. Repeated occurrences in the same
context share that work, different contexts are charged independently, and
suppressed subtrees contribute nothing. Active external components and cyclic
local-assembly graphs are rejected before resolver or kernel work. The staged
slice does not provide external-document evaluation, per-body materials, mates,
joints, DOF, motion, contact, interference/collision, assembly topology,
aggregate geometric measurement, or exact assembly STEP/BREP export. Its
aggregate mesh, STL, and OBJ are approximate/lossy tessellation views, and
Document v7 remains repository-only.

## Runtime parameter overrides

Explicit `EvaluationOptions.parameters` can further specialize the selected
configuration. This is useful for one-off builds without adding a permanent
named variant. Keep named release/manufacturing variants in the document when
they need reviewable identity and repeatability.

## Impact and caching contexts

Each named configuration is an independent effective evaluation context for
design-impact and feature-hash analysis. A material or suppression change may
affect only some contexts. See
[design impact and hashes](/analysis/design-impact-and-hashes).
